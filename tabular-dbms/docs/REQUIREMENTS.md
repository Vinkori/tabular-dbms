# Вимоги та критерії перевірки

Система типу 1; типи варіанта 0 (`color`, `colorInvl`), операція варіанта 5
(вилучення повторюваних рядків).

| ID | Вимога | Критерій приймання | Файли тестів |
|---|---|---|---|
| FR-01 | Створення та відкриття БД | Непорожня назва, UUID, повторне читання | test_services.py, test_api.py, test_storage.py |
| FR-02 | Створення таблиці | Принаймні одна колонка; унікальні назви; дозволені типи | test_rows.py, test_services.py, test_api.py |
| FR-03 | Видалення таблиці | Таблиця недоступна після видалення; інші збережені | test_services.py, test_api.py |
| FR-04 | Перевірка шести типів | Коректні значення нормалізуються, некоректні відхиляються | test_types.py |
| FR-05 | Додавання рядка | Всі колонки без зайвих; помилка не додає рядок | test_rows.py, test_api.py |
| FR-06 | Перегляд і редагування | Повертаються схема та рядки; PATCH зберігає UUID | test_rows.py, test_services.py, test_api.py |
| FR-07 | Вилучення повторів | Враховуються всі значення; перші входження й порядок збережені | test_duplicates.py, test_services.py, test_api.py |
| FR-08 | Збереження/відновлення | Типи, UUID та порядок збережені; пошкоджені документи відхиляються | test_storage.py |
| FR-09 | Імпорт/експорт | Експортований документ імпортується як нова база | test_storage.py, test_api.py |
| FR-10 | Два клієнти та спільний API | Web і desktop використовують серверні операції | test_web.py, test_desktop.py, ручний сценарій |

## Ручний сценарій демонстрації

1. Перевірити `/api/health`, `/` та `/docs`.
2. Імпортувати `examples/demo_database.json` через вебклієнт.
3. Перевірити 3 рядки та 6 колонок у таблиці `Samples`.
4. Вилучити повтори: `removed = 1`, `remaining_rows = 2`.
5. Додати коректний рядок, змінити його й перевірити результат.
6. Спробувати RGB-канал `256`: зміна має бути відхилена.
7. Відкрити ту саму таблицю в desktop і оновити дані.
8. Експортувати базу, перезапустити сервер і повторно відкрити її.
9. Видалити таблицю та перевірити її відсутність після оновлення.

Це критерії й сценарій навчальної перевірки, а не твердження про проведене
користувацьке приймання (UAT) у зовнішнього замовника.
